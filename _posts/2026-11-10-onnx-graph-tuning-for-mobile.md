공개된 사전학습 모델을 가져와 모바일에서 돌리면, 모델 자체보다 **모델 주변**에서 시간이 새는 경우가 많습니다. 레이아웃 변환, 같은 모델의 반복 호출, CPU에서 하는 전처리, 여러 개의 출력 텐서 같은 것들입니다. 가중치와 연산 구조는 그대로 두고 ONNX 그래프만 정리해서 추론 시간을 줄이는 네 가지 기법을 정리합니다. 여러 모델을 잇는 파이프라인에서 네 가지를 함께 적용했을 때, 기기에 따라 파이프라인 시간이 2~4배 줄었습니다.

## 1. 레이아웃 통일 — NHWC/NCHW 혼재 없애기

다른 프레임워크에서 변환한 모델은 입력이 NHWC(TensorFlow 계열)이고, 같은 파이프라인의 다른 모델은 NCHW(PyTorch 계열)인 경우가 흔합니다. 그러면 그래프 앞뒤에 `Transpose`가 끼고, 런타임이 메모리 재배치를 매번 합니다.

- 파이프라인 전체를 한 레이아웃(NCHW)으로 통일하고, 입력 직후의 `Transpose`와 불필요한 `Reshape`를 제거합니다
- 입력을 만드는 쪽(카메라 프레임 → 텐서)에서 처음부터 목표 레이아웃으로 채우면 변환이 아예 사라집니다
- 바꾼 뒤에는 원본과 출력이 같은지 반드시 비교합니다(아래 검증)

## 2. 배치 추론 — 같은 모델을 두 번 부르지 않기

좌·우처럼 같은 모델을 두 번 호출하는 구조라면, 두 입력을 batch 2로 묶어 한 번에 돌립니다.

- 한쪽 입력은 좌우 반전해 같은 방향으로 맞춘 뒤 묶고, 출력에서 다시 반전을 되돌립니다
- 호출 횟수가 줄면 커널 실행·동기화·스케줄링 오버헤드도 같이 줄어듭니다
- 그래프의 배치 차원이 고정 1로 박혀 있으면 동적 배치(또는 2)로 바꿔야 합니다

## 3. 전처리를 그래프 안으로

얼굴이나 객체 영역을 잘라(crop) 크기를 맞추는(resize) 전처리를 앱 코드(CPU)에서 하면, 큰 이미지를 CPU로 가져와 처리한 뒤 다시 넘기게 됩니다.

- crop·resize를 ONNX 연산자(`Slice`, `Resize` 등)로 그래프 앞에 넣어 추론 백엔드에서 처리합니다
- 잘라낼 위치(오프셋)는 작은 입력 텐서로 따로 넘깁니다
- 이미지 왕복과 CPU 연산이 사라지고, 전처리 구현이 플랫폼마다 달라서 생기는 미세한 차이도 없어집니다

## 4. 출력 병합과 평탄화

검출·랜드마크 모델은 출력이 여러 개인 경우가 많습니다. 출력마다 따로 읽으면 결과를 가져올 때마다 동기화와 복사가 일어납니다.

- 쓰지 않는 출력과 그 출력만을 위한 연산은 그래프에서 지웁니다
- 남은 출력들을 각각 평탄화(`Flatten`)해 이어 붙여(`Concat`) **텐서 하나**로 만듭니다
- 받는 쪽은 각 출력의 모양과 순서를 이미 알고 있으므로, 오프셋으로 잘라 원래 구조대로 해석합니다

이렇게 하면 결과 전달이 추론당 한 번으로 줄어듭니다. 특히 GPU 백엔드에서 결과를 CPU로 읽어 오는 비용이 클 때 효과가 큽니다([관련 글](/blog/small-model-gpu-readback/)).

## 같은 정리라도 런타임마다 효과가 다르다 — PRelu 기울기 Expand

MediaPipe 계열 얼굴 랜드마크 모델을 변환해 보면, PRelu의 채널별 기울기(`[1, C, 1, 1]`)를 `Expand`로 특징맵 크기(`[1, C, H, W]`)까지 펼쳐서 넣는 그래프가 나오는 경우가 있습니다. 변환 도구가 남긴 흔적으로 보입니다.

- **어떤 런타임은 로드할 때 이 상수를 미리 접고 PRelu를 채널별로 처리합니다.** 이 경우 Expand를 지워도 파일만 약 40% 작아지고 실행 시간은 그대로였습니다
- **ONNX Runtime CPU에서는 달랐습니다.** 그래프 최적화가 Expand를 상수로 접으면서 **특징맵과 같은 크기의 기울기 텐서**를 만들고, PRelu는 같은 크기 텐서 두 개를 읽는 일반 원소별 경로를 탑니다. 노드별 프로파일을 보니 계산량이 거의 없는 PRelu가 커널 시간의 약 3할을 쓰고 있었습니다
- 기울기를 Expand 없이 채널별 상수로 바로 넘기도록 그래프를 고치면(ONNX 브로드캐스트 규칙상 곱해지는 값은 같음) 출력은 비트 단위로 같고, 랜드마크 추론 시간이 **약 24% 줄었습니다**

교훈은 두 가지입니다. "노드가 줄었다"가 아니라 **실기기 시간**으로 판단할 것, 그리고 **같은 모델이라도 런타임을 바꾸면 병목이 다른 곳에 생긴다**는 것. 런타임을 바꿀 때는 노드별 프로파일을 다시 봐야 합니다([모바일 CPU 추론 최적화 점검표](/blog/mobile-cpu-inference-checklist/)).

## 검증 — 출력이 같은지부터

그래프를 고친 뒤에는 속도보다 먼저 **출력이 원본과 같은지** 확인합니다.

- 같은 입력 묶음을 원본과 수정본에 넣고 출력의 최대 절대 오차를 비교합니다. 레이아웃·배치·평탄화처럼 수학적으로 같은 변환은 **비트 단위로 같아야** 합니다
- 런타임이 둘 이상이면(예: ONNX Runtime과 엔진 내장 추론기) 양쪽에서 모두 비교합니다
- 그다음 실기기에서 중앙값과 p95 시간을 잽니다. 기법별 기여도를 따로 재지 않았다면, 결과는 "함께 적용해서" 몇 배로만 말합니다

## 정리

| 기법 | 줄이는 것 |
|---|---|
| 레이아웃 통일 | Transpose·메모리 재배치 |
| 배치 추론 | 같은 모델 반복 호출 오버헤드 |
| 전처리 내장 | 이미지 왕복·CPU 전처리 |
| 출력 병합·평탄화 | 결과 전달·동기화 횟수 |

모델을 줄이거나 양자화하기 전에, 이 네 가지로 출력은 그대로 두고 얻을 수 있는 몫부터 챙기는 것을 권합니다.
