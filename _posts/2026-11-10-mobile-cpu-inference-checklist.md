"추론 최적화 기법" 목록을 찾아보면 상당수가 LLM(Attention, KV 캐시, 토큰 생성)이나 GPU 서버용입니다. 휴대폰 CPU에서 한 번에 한 프레임씩 도는 **작은 CNN 여러 개**(검출·랜드마크·자세 등, MediaPipe 계열)에 실제로 무엇이 통하는지, 하나씩 대입해 본 결과를 정리했습니다. 기준은 하나입니다. **출력이 그대로인 개선을 먼저 다 하고, 출력이 바뀌는 기법은 따로 검증한다.**

## 1. 통한 것

### 런타임 교체 — 모델 계열에 맞는 런타임

같은 모델을 ONNX Runtime CPU 대신 **TFLite(LiteRT) + XNNPACK**으로 돌리자 랜드마크·검출·자세 모델이 각각 20~40% 빨라졌습니다.

- 이 모델들은 depthwise 3×3 → 1×1 → 잔차 → PRelu 블록 구조이고, 원래 MediaPipe가 쓰는 런타임이 TFLite + XNNPACK입니다
- XNNPACK은 NHWC 배치로 처음부터 끝까지 돌고 PRelu를 자체 커널로 처리합니다. ORT CPU는 NCHW 기본에 채널별 PRelu가 별도 패스라 메모리를 한 번 더 읽습니다
- **함정**: TFLite C API의 기본 인터프리터는 XNNPACK을 자동으로 붙이지 않습니다. 명시적으로 delegate를 붙이지 않으면 오히려 두 배 느려졌습니다
- TFLite로 변환되지 않는 동적 Slice·Resize(눈 크롭) 부분은 원래 ONNX 그래프에서 그 부분만 잘라 작은 ORT 그래프로 돌리는 **하이브리드**로 처리했습니다. 반대로 작은 분류 모델 하나는 TFLite에서 더 느려 ORT에 남겼습니다. 모델별로 잰 뒤 고릅니다
- 변환 후에는 실제 입력 수백 세트로 원래 모델과 출력을 비교했습니다

### 전처리 재구성 — 비트 단위로 같게

카메라 프레임을 모델 입력으로 만드는 C++ 전처리(레터박스·크롭·회전·좌우반전·쌍선형 보간)를 다시 짰습니다.

- 출력 픽셀마다 반복하던 회전·형식 분기를 템플릿으로 **행 바깥으로** 빼고
- 열 방향 보간 좌표·가중치를 한 번만 계산해 **행마다 재사용**했습니다
- 계산 순서와 산술을 그대로 둬 결과가 **비트 단위로 같고**(형식 3 × 회전 4 × 미러 2 = 96가지 조합 자동 검사), 전처리 시간은 절반 이하로 줄었습니다

### 그래프 정리 — 런타임이 놓친 것만

노드별 프로파일에서 계산량이 거의 없는 PRelu가 커널 시간의 약 3할을 쓰는 것을 찾았고, 원인인 기울기 `Expand`를 없애 랜드마크를 약 24% 줄였습니다(자세한 내용은 [ONNX 그래프 손보기](/blog/onnx-graph-tuning-for-mobile/)).

### 스레드 수 — 큰 코어 수에 맞춰

큰 코어 4개(큰 코어 3 + 프라임 1)인 SoC에서 추론 스레드를 2 → 3으로 늘리자 빨라졌고, 4로 늘리면 렌더 스레드와 큰 코어를 다투고 작은 모델은 분할 비용이 커져 오히려 느려졌습니다. **코어 구성을 보고 정하고, 모델 크기별로 잽니다.**

## 2. 의외의 변수 — 앱 안에서는 CPU 클럭이 안 올라간다

같은 모델이 앱 밖 단독 벤치마크에서는 빠른데 앱 안에서는 거의 두 배 느렸습니다. 원인은 **CPU 클럭**이었습니다.

- 추론은 100ms마다 20ms 남짓 짧게 돕니다. Android 클럭 조절기(schedutil)가 클럭을 올리기 전에 일이 끝나 큰 코어가 낮은 클럭에 머뭅니다
- 오히려 게임처럼 렌더링이 계속 도는 상황에서는 클럭이 이미 올라가 있어 **부하가 있을 때 추론이 더 빨랐습니다**
- **ADPF(Android Performance Hint)**로 목표 시간을 실제 틱보다 짧게 알려 주면 부하가 없을 때 클럭이 올라가 틱이 줄었습니다. 목표가 실제보다 길면 효과가 없습니다
- 교훈: 벤치마크는 **실제 앱과 같은 부하 조건**에서 잽니다. 빈 앱에서 잰 숫자는 실제와 다릅니다. 클럭을 더 올리는 설정은 배터리·발열과 맞바꾸는 것이라 장시간 측정 뒤 판단합니다

## 3. 시도했지만 기각한 것

| 기법 | 결과 |
|---|---|
| FP16 (ORT CPU) | FP16 PRelu 커널이 없어 2배 느림, 출력도 크게 바뀜 |
| INT8 정적 양자화(실제 입력 보정) | 합성곱은 빨라지지만 PRelu 앞뒤 변환 때문에 랜드마크 전체는 느려짐, 출력 변화 큼. 자세 모델만 이득 |
| NNAPI | 일부 연산 미지원으로 그래프가 쪼개져 CPU보다 10배 이상 느림 |
| 모바일 NPU/DSP 실행 공급자 | 해당 SoC 세대의 가속기가 필요한 연산 경로를 지원하지 않음, GPU 경로는 CPU보다 느림 |
| 희소화(가지치기) | 런타임의 희소 경로가 이 구조에서 타지 않음, 재학습 없이 가지치기하면 출력이 크게 틀어짐 |
| 모델 병합 | 실행당 오버헤드가 아주 작아 이득 없음 |

## 4. 구조상 해당하지 않는 것

Speculative Decoding, KV 캐시·PagedAttention, FlashAttention, Continuous Batching, Prompt Caching 같은 기법은 **토큰을 하나씩 생성하는 Transformer**나 **여러 요청을 묶는 서버**용입니다. 한 번 실행으로 결과가 나오고 요청이 프레임 하나뿐인 작은 CNN에는 해당하지 않습니다. 목록을 그대로 따라가지 말고, 모델 구조와 실행 환경에 대입해 걸러야 합니다.

## 5. 남은 큰 이득은 출력을 바꾸는 쪽에만 있다

출력이 그대로인 개선을 다 하고 나면, 남은 시간의 대부분은 합성곱 자체입니다. 더 줄이려면 입력 해상도 축소, Early Exit(움직임이 없을 때 일부 모델 건너뛰기), 양자화, 경량 모델 재설계·증류처럼 **결과가 바뀌는** 방법뿐이고, 이건 정확도 재검증과 함께 별도 결정으로 다룹니다.

## 정리

| 구분 | 기법 |
|---|---|
| 적용(출력 그대로) | 모델 계열에 맞는 런타임(TFLite+XNNPACK 하이브리드), 비트 동일 전처리 재구성, 그래프 정리, 큰 코어 수에 맞춘 스레드 |
| 조건부 | ADPF 클럭 힌트(부하 없을 때 효과, 배터리와 맞바꿈) |
| 기각 | FP16·INT8(이 구조에서), NNAPI, NPU/DSP(해당 세대), 희소화, 모델 병합 |
| 해당 없음 | LLM·서버용 기법 전반 |
