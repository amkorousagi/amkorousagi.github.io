모바일 시선 추적 파이프라인을 게임 엔진의 내장 추론 엔진으로 옮긴 뒤, 백엔드(CPU, GPU 컴퓨트, GPU 픽셀 셰이더)별로 두 가지 최적화를 켜고 끄며 쟀습니다.

1. **배치 추론**: 왼쪽·오른쪽 눈 크롭을 batch 2로 묶어 홍채 모델을 한 번만 실행
2. **NMS를 모델에 붙이기**: 얼굴 검출 후처리(Non-Maximum Suppression)를 모델 그래프 안에 넣어 백엔드에서 실행

## 결과 요약

| 백엔드 | NMS 모델에 포함 | 양눈 배치 | 결과 |
|---|---|---|---|
| CPU | – | – | 안정적인 화면 fps, 1회 추론은 가장 느린 편 |
| GPU 컴퓨트 | – | – | CPU보다 오히려 느림, 피크 때 fps 절반 |
| GPU 픽셀 | – | – | 추론은 빠르지만 fps가 출렁임 |
| GPU 픽셀 | **빼고** | **적용** | **fps 안정 + 1회 추론이 기존의 약 1/3** |

## 배치: GPU에서는 듣고 CPU에서는 안 들었다

- GPU 백엔드에서는 양눈 배치로 홍채 단계 시간이 **거의 절반**이 됐습니다. 같은 커널이 두 입력을 병렬로 처리하고, 실행·동기화 오버헤드가 한 번만 들기 때문입니다
- CPU 백엔드에서는 **효과가 거의 없었습니다.** 이 엔진의 CPU 경로는 배치 두 개를 결국 순차로 계산했고, 작은 모델이라 실행 오버헤드도 크지 않았습니다

배치는 "항상 빠르다"가 아니라 **병렬 실행 여지와 호출 오버헤드가 있을 때** 빠릅니다.

## NMS: GPU에 붙이면 전체가 느려졌다

직관적으로는 후처리까지 GPU에서 하면 결과를 CPU로 가져오는 양이 줄어 빨라질 것 같았습니다. 계산해 보면 검출 출력(앵커 수천 개 × 몇 개 값)을 그대로 가져와도 모바일 메모리 대역폭으로는 수 ms 수준입니다. 반면 NMS는 정렬·비교·분기가 많은 연산이라 GPU에 맞지 않고, 같은 큐의 **다른 작업까지 늦췄습니다.** NMS를 빼고 CPU에서 하자 오히려 빨라졌습니다.

## 측정 방법에서 챙긴 것

- **최빈 시간과 최악 시간을 따로**: 18번 중 15번 나온 시간(최빈)과 얼굴을 다시 찾을 때의 시간(최악)을 구분해 기록했습니다([최악 지연](/blog/worst-case-latency/))
- **테스트 화면과 실제 사용 화면 둘 다**: 실제 화면에서는 렌더링 부하 때문에 숫자가 달라집니다. 저사양 기기에서는 차이가 컸습니다
- **곁가지 비용도 숫자로**: 디버그 시각화를 켜면 요소당 약 1ms씩, 텐서 재사용·다음 프레임 대기 같은 안정화 처리도 각각 몇 ms가 붙었습니다. 프로파일러와 디버그 빌드 자체도 시간을 더하므로 릴리스 빌드에서 다시 확인합니다
- **기기 편차**: 최신 태블릿에서 GPU 픽셀이 최선이었지만, 저사양 기기에서는 GPU 백엔드가 CPU보다 몇 배 느려 **CPU가 유일한 선택**이었습니다. 백엔드는 기기별로 고르거나, 가장 느린 기기 기준으로 정해야 합니다

## 정리

- 배치는 병렬 여지와 호출 오버헤드가 있는 백엔드에서만 이득이다
- 분기·정렬이 많은 후처리(NMS)는 GPU에 올리지 않는 편이 나을 수 있다 — 전송 비용을 계산해 보면 작다
- 같은 최적화도 백엔드·기기마다 따로 잰다

이후 더 넓은 기기에서 다시 재 보니 CPU 백엔드가 전반적으로 가장 안정적이었고, 그 이유는 [GPU readback 비용](/blog/small-model-gpu-readback/)에 정리했습니다.
