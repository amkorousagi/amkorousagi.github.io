카메라 프레임을 게임 엔진이나 추론 모델로 넘기는 Android 파이프라인은 대략 이렇게 생겼습니다.

```text
Camera2 → SurfaceTexture(OES 외부 텍스처) → updateTexImage
       → 네이티브 플러그인이 OES를 FBO 텍스처로 복사 (패스 1)
       → 엔진이 회전·미러를 적용해 다시 블릿 (패스 2)
       → 모델 입력 크기로 축소(레터박스) → 추론
```

기능을 고치는 PR에서는 정확성을 먼저 챙기고, 효율 문제는 다음 PR 후보로 정리해 두는 경우가 많습니다. 그때 "어디부터 손댈지"를 측정 전에 **계산으로** 좁혀 두면 프로파일링 시간이 크게 줄어듭니다. 아래는 그렇게 정리한 후보와 근거입니다.

## 1. 같은 해상도의 2패스 블릿 — 가장 큰 후보

패스 1이 1080p 전체를 복사하고, 패스 2가 같은 해상도를 회전만 하려고 다시 블릿한다면 패스 2는 순수한 낭비입니다.

- 1920×1080 RGBA8 한 장 = 약 **8.3MB**. 패스 하나가 읽기 8.3MB + 쓰기 8.3MB
- 30fps면 패스 하나에 약 **0.5GB/s**의 메모리 대역폭
- 타일 기반 모바일 GPU에서는 이 대역폭이 발열과 배터리를 좌우합니다

해결은 회전·미러를 패스 1의 셰이더 UV 변환(2×2 행렬 uniform)으로 넣고, FBO를 처음부터 회전된 해상도로 만드는 것입니다. 중간 텍스처와 렌더 타깃 전환이 한 번씩 사라집니다. 대신 이 텍스처를 쓰는 모든 소비자(미리보기, 레터박스 계산)의 해상도·방향 가정을 전수 확인해야 합니다.

## 2. 디스플레이 주사율로 도는 복사 루프

렌더 루프는 60~120Hz로 도는데 카메라는 30fps라면, 새 카메라 프레임 하나당 **같은 복사·블릿이 2~4번** 반복됩니다. `SurfaceTexture.getTimestamp()`가 전진하지 않았으면 그 프레임의 복사를 건너뛰는 것만으로 카메라 경로 GPU 비용이 1/2~1/4이 됩니다. 건너뛰어도 출력 텍스처는 직전 프레임을 유지하므로 동작은 같습니다. 난이도 대비 효과가 가장 좋은 후보입니다.

## 3. 카메라 요청 해상도

실기기 로그를 보니 해상도 선택 코드가 주석과 달리 **가장 큰 해상도(약 8MP)**를 고르고 있었습니다. 모델 입력이 수백 픽셀 크기라면, 카메라 요청 자체를 1080p 이하로 낮추는 것이 ISP·메모리 대역폭·`updateTexImage` 비용을 원천적으로 줄입니다. 1·2번보다 효과가 클 수도 있습니다. 다만 입력 해상도가 모델 정확도에 주는 영향은 별도로 확인해야 합니다.

## 4. 작은 것들

- **CommandBuffer 재사용**: 매 프레임 `Clear()` 후 같은 명령을 다시 기록하면 기록 비용과 박싱 할당(GC 스파이크)이 생깁니다. 참조가 바뀔 때만 재기록합니다
- **GL 상태 무효화 빈도**: 네이티브 플러그인이 GL 상태를 바꾼 뒤 엔진에 상태를 다시 적용하게 하는 호출(`GL.InvalidateState` 등)은 보험 성격이 있어, 줄이려면 회귀 감시 장치와 함께 마지막에 합니다
- **상태 조회 줄이기**: 프레임마다 `glGetIntegerv`를 여러 번 부르면 일부 드라이버에서 동기화 비용이 생길 수 있습니다. 플러그인이 결정적으로 설정하는 상태는 조회 없이 복구합니다

## 측정 계획 — 계산은 우선순위일 뿐

계산은 어디를 볼지 정해 줄 뿐이고, 채택은 측정으로 합니다.

1. 기준선: 저사양 기기에서 렌더 스레드 프로파일, `adb shell dumpsys gfxinfo` 프레임 시간, 10분 세션의 발열·배터리
2. 항목별 켜고 끄기 비교 — 대역폭 항목(1~3번)은 가능하면 GPU 벤더 프로파일러(Snapdragon Profiler, Mali Streamline)로
3. 회귀 감시: 카메라 화면 밝기 진단 로그, 콜드 스타트 스모크 테스트

## 정리

| 후보 | 근거 | 효과 | 난이도·위험 |
|---|---|---|---|
| 2패스 블릿 제거 | 프레임당 약 16MB 읽기·쓰기 | 큼 | 중 · 소비자 가정 확인 |
| 카메라 fps에 맞춰 복사 스킵 | 프레임당 2~4회 중복 | 큼 | 하 · 낮음 |
| 카메라 해상도 낮추기 | 8MP → 1080p | 매우 클 수 있음 | 하 · 정확도 확인 |
| CommandBuffer 재사용 | 매 프레임 재기록 | 작음 | 하 · 낮음 |
| 상태 무효화·조회 축소 | 프레임당 수십 µs | 작음 | 하 · 중(보험 감소) |

이렇게 카메라 경로를 줄여 두면, 추론 쪽 최적화([GPU readback](/blog/small-model-gpu-readback/), [ONNX 그래프](/blog/onnx-graph-tuning-for-mobile/))의 효과도 더 깨끗하게 측정됩니다.
