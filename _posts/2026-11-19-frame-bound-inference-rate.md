게임 엔진 앱 안에서 비전 모델을 "100ms마다(10Hz)" 돌리도록 해 두었는데, 측정해 보니 화면 목표를 30fps로 낮춘 순간 실제 추론이 10Hz를 못 지켰습니다. 20Hz로 올리면 더 심했습니다. 추론 자체는 충분히 빨랐습니다. 원인은 **추론이 렌더 프레임 경계에 묶여 있다**는 구조였습니다.

## 1. 렌더 루프 안의 추론은 프레임마다 한 번만 깨어난다

엔진 내장 추론(예: Unity의 추론 엔진)을 일반적인 방식으로 쓰면 흐름이 이렇습니다.

1. 매 프레임 `Update`에서 "지난 추론 시작 후 100ms가 지났나?"를 확인
2. 지났으면 입력 텐서를 만들고 추론을 예약
3. 이후 프레임마다 "결과가 나왔나?"를 확인하고, 나왔으면 읽어 와 후처리

여기서 **확인은 프레임마다 한 번**입니다. 시작 조건이 프레임 중간에 충족돼도 다음 프레임까지 기다리고, 결과가 프레임 중간에 나와도 다음 프레임에야 읽습니다. 그래서 실제 간격은 원하는 간격을 **프레임 간격의 배수로 올림**한 값이 됩니다.

## 2. 계산해 보기

프레임 간격을 `F`, 원하는 추론 간격을 `T`라 하면, 실제 간격은 대략

```
실제 간격 ≈ ceil(T / F) × F   (+ 결과 대기로 한 프레임 더 밀리는 경우)
```

| 목표 fps (F) | 원하는 주기 (T) | ceil(T/F) | 실제 간격 | 실제 주기 |
|---|---|---|---|---|
| 60fps (16.7ms) | 10Hz (100ms) | 6 | 100ms | 10Hz (딱 맞음) |
| 60fps (16.7ms) | 20Hz (50ms) | 3 | 50ms | 20Hz (딱 맞음) |
| 30fps (33.3ms) | 10Hz (100ms) | 3 | 100ms | 10Hz → **가끔 4프레임이면 7.5Hz**, 평균 9Hz 안팎 |
| 30fps (33.3ms) | 20Hz (50ms) | **2** | **66.7ms** | **15Hz** |

- 30fps에서 20Hz를 요청하면 50ms는 1.5프레임이라 2프레임(66.7ms)으로 올림되어 **15Hz가 상한**입니다
- 10Hz는 계산상 3프레임으로 딱 맞지만, 프레임 시간이 조금만 흔들려도(33.3ms보다 살짝 짧은 프레임이 끼면 100ms가 아직 안 지남) 4프레임을 기다리게 되어 평균이 10Hz보다 낮아집니다
- 60fps에서는 50·100ms가 프레임의 정수배라 잘 맞지만, 부하로 프레임이 길어지면 같은 이유로 주기가 내려갑니다

실측에서도 실제 주기가 이 표의 계산과 같은 자리에서 막혔고, 이 현상은 **저사양·고사양 기기를 가리지 않고** 나타났습니다. 기기가 빠르다고 해결되는 문제가 아니라는 뜻입니다.

## 3. 해결 — 추론을 자기 시계로 돌린다

추론을 렌더 루프에서 꺼내 **전용 스레드**로 옮겼습니다(C++ 코어, 자세한 구조는 [하나의 C++ 추론 코어를 Unity와 React Native에서 같이 쓰기](/blog/cpp-inference-core-c-api/)).

- 추론 스레드는 자기 시계(`steady_clock`)로 100ms마다 깨어나 최신 프레임 하나를 가져와 추론합니다. 프레임 경계를 기다리지 않습니다
- 결과는 "최신값 1칸"에 쓰고 일련번호를 올립니다. 렌더 루프는 매 프레임 그 칸을 들여다보고 새 값이 있을 때만 가져갑니다. 렌더 쪽 비용은 구조체 복사 하나입니다
- 결과: 같은 30fps 목표에서도 **설정한 10·20Hz를 그대로 지켰습니다**. 렌더 프레임과 추론이 서로를 기다리지 않으니, 화면 끊김(하위 1% fps)도 함께 줄었습니다

전용 스레드도 공짜는 아닙니다. 같은 CPU 코어를 렌더링과 나눠 쓰므로 추론 스레드 수를 너무 늘리면 오히려 화면이 끊깁니다. 그 부분은 [추론 스레드를 줄였더니 화면이 덜 끊겼다](/blog/inference-threads-vs-frame-drops/)에 정리했습니다.

## 4. 엔진 안에서 고쳐야 한다면

전용 스레드로 옮길 수 없는 상황이면, 적어도 다음은 할 수 있습니다.

- **시작 조건을 프레임 안 여러 지점에서 확인**: `Update`뿐 아니라 `LateUpdate`, 프레임 끝에서도 확인하면 평균 대기가 줄어듭니다
- **누적 시간 기준으로 다음 시작을 잡기**: "마지막 시작 + T"가 아니라 "기준 시각 + n·T"로 잡으면 올림 오차가 쌓이지 않고 평균 주기가 목표에 가까워집니다(각 간격은 여전히 프레임 배수)
- **주기를 프레임 간격의 배수로 고르기**: 30fps면 66.7ms(15Hz)나 100ms(10Hz)처럼. 맞지 않는 값을 요청하면 어차피 올림됩니다
- **실제 주기를 로그로 남기기**: 설정값이 아니라 실제로 끝난 추론 횟수/초를 기록해야 이 문제가 보입니다

## 정리

| | 렌더 루프 안 추론 | 전용 스레드 추론 |
|---|---|---|
| 깨어나는 시점 | 프레임마다 한 번 | 자기 시계(설정 주기) |
| 실제 주기 | 프레임 간격의 배수로 올림. 30fps에서 20Hz → 최대 15Hz | 설정값 유지 |
| 렌더 프레임 비용 | 예약·결과 확인·후처리가 메인 스레드에 | 결과 구조체 복사 하나 |
| 주의 | 목표 fps를 낮추면 추론 주기도 같이 떨어짐 | 추론 스레드 수가 렌더와 코어를 다툼 |

설정값이 아니라 **실제로 몇 번 돌았는지**를 재는 것, 그리고 그 숫자가 왜 그렇게 나오는지 계산으로 설명할 수 있어야 한다는 것이 이번에 배운 점입니다.
