같은 시선 추적 파이프라인을 두 가지 앱 프레임워크(Flutter, Unity)로 구현해 여러 기기에서 쟀을 때, 평균 지연만 보면 쓸 만해 보이는 조합에서도 사용자는 "가끔 멈춘다"고 느꼈습니다. 그래서 측정 기준을 **최악 지연**으로 바꿨습니다.

## 1. 최악 지연은 어디서 생기나

틱을 단계별로 나눠 보니, 최악 지연은 대부분 **얼굴을 다시 찾는 틱**에서 나왔습니다.

- 평소에는 직전 얼굴 위치를 이용해 랜드마크만 돌립니다
- 얼굴을 놓치거나 주기적으로 재검출할 때는 **얼굴 검출 + 랜드마크 + 후처리**가 한 틱에 몰립니다
- 그 틱만 평소의 1.5~2배가 걸리고, 그동안 화면이나 판정이 멈춘 것처럼 보입니다

평균은 이런 틱을 희석합니다. 100번 중 5번만 길어도 평균은 거의 변하지 않지만, 사용자는 그 5번을 기억합니다.

## 2. 무엇을 재나

| 지표 | 의미 |
|---|---|
| 중앙값(최빈값) | 평소 체감 |
| p90·p99, 최대 | 끊김 체감 |
| 얼굴 재검출 틱의 시간 | 최악의 주원인 |
| 화면 fps와 긴 프레임 비율 | 지연이 렌더링까지 번지는지 |

같은 조건을 맞추기 위해 **가장 느린 목표 기기**와 **실제 사용 화면**(게임 렌더링이 도는 상태)에서 잽니다. 데모 화면에서 잰 숫자는 대개 낙관적입니다.

## 3. 줄이는 방법 — 작업을 프레임에 나눠 싣기

**큐로 분산**: 한 틱에 몰리는 무거운 작업(검출, 일부 후처리)을 다음 프레임들로 나눠 실행했습니다. 한 구현에서는 이것만으로 최악 지연이 300ms대에서 250ms 안쪽으로, 평균은 절반 수준으로 내려갔습니다.

**이미지 연산을 GPU로**: 다른 구현에서는 크롭·리사이즈 같은 이미지 연산을 CPU 라이브러리 대신 셰이더로 옮겨 기기에 따라 큰 폭으로 줄었습니다.

흥미로운 점은 **두 구현이 서로 다른 최적화만 하고 있었다**는 것입니다. 하나는 작업 분산만, 다른 하나는 이미지 연산 최적화만. 비교표를 만들고 나서야 각자 다른 쪽의 기법을 가져올 수 있다는 게 보였습니다.

## 4. 아직 시도하지 않은 조합을 적어 둔다

측정 당시 다 해 보지 못한 설정(런타임의 CPU 메모리 할당 방식, GPU 실행 공급자의 FP16·NHWC 옵션, 그래픽 API Vulkan/OpenGL 선택)을 표에 "미시도"로 남겨 두었습니다. 다음 측정의 출발점이 되고, "이미 다 해 봤다"는 착각을 막아 줍니다.

## 정리

- 실시간 시스템은 평균이 아니라 p90·최대·긴 프레임 비율로 본다
- 최악은 대개 특정 종류의 틱(재검출)에 몰려 있다 — 그 틱을 따로 잰다
- 무거운 작업은 여러 프레임에 나눠 싣는다
- 구현이 여러 개라면 서로의 최적화를 표로 맞대어 본다
