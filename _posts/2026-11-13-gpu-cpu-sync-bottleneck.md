소아 근시 디지털 치료기기 앱에는 태블릿 전면 카메라로 아이의 시선과 화면까지의 거리를 재는 파이프라인이 들어 있습니다. 얼굴 검출 → 얼굴 랜드마크·홍채 → 고개 각도 → 시선·거리 순서로 모델 여러 개가 이어지고, 모두 기기 안에서 돕니다. 아이 얼굴 영상을 기기 밖으로 보내지 않는 것이 설계 제약이었습니다.

이 글은 Android에서 이 파이프라인의 추론 시간을 **120–300ms에서 42–48ms로** 줄인 과정입니다. 모델을 바꾸거나 줄이지 않았습니다. 바꾼 것은 **결과를 어디서 계산하고 어떻게 가져오느냐**였습니다.

## 증상

- Galaxy Tab S7에서 추론 1회가 130–150ms 걸렸고, 1분쯤 지나면 260–300ms로 밀리면서 시선이 몇 초씩 멈췄습니다
- 앱은 Unity 게임이라 같은 시간에 렌더링도 돕니다. 시선이 멈출 때 화면도 함께 버벅였습니다

## 처음 의심한 것

"모델이 무겁다"였습니다. 모델 크기를 줄이거나 입력 해상도를 낮추는 쪽부터 떠올리기 쉽습니다. 그런데 모델 연산량은 바뀐 게 없는데 시간이 지날수록 느려진다는 점이 맞지 않았습니다. 연산량이 원인이라면 처음부터 끝까지 일정하게 느려야 합니다.

## 측정해 보니

추론 한 번을 단계별로 쪼개 시간을 찍어 보니, GPU에서 계산을 끝낸 결과를 **CPU로 가져오는 순간**에 시간이 몰려 있었습니다.

- GPU 백엔드에서 결과 텐서를 CPU로 읽어 오려면 GPU 작업이 끝날 때까지 기다려야 합니다(동기화)
- 이 기다림이 **렌더링 스레드를 막았습니다.** 게임 렌더링과 추론이 같은 GPU를 쓰니 서로 밀립니다
- 모델마다 출력 텐서가 여러 개라, 한 번 추론에 **동기화가 여러 번** 일어났습니다
- 추론 루프는 일정 시간 쉬었다 다시 도는 구조였는데, 한 번 밀리면 다음 차례도 밀리면서 지연이 쌓였습니다

## 한 일

**1. 출력 텐서를 하나로 합치기**
모델 그래프 끝에서 여러 출력을 평탄화(flatten)해 하나의 텐서로 이어 붙였습니다. 받는 쪽은 출력 구조를 이미 알고 있으니 위치만으로 다시 나눠 읽으면 됩니다. 동기화가 모델당 한 번으로 줄었습니다.

**2. 백엔드를 다시 고르기 — GPU가 빠르다는 가정을 검증**
GPU 백엔드를 CPU 백엔드로 바꿔 보니 실기기에서 바로 빨라졌습니다. 우연이 아닌지 확인하려고, 나중에 같은 절차로 CPU 백엔드와 GPU 백엔드 두 종류를 기기별로 다시 측정했습니다. 측정 전에 "지연이 20% 이상 줄고 화면 프레임이 유지될 것"이라는 판정 기준을 먼저 정했습니다. 결과는 테스트한 환경 모두에서 **CPU 백엔드가 가장 빨랐습니다.** 이 크기의 모델은 GPU 연산 이득보다 GPU→CPU 전달 비용이 더 컸고, GPU는 게임 렌더링과도 경쟁했습니다.

**3. 결과를 비동기로 받기**
CPU 백엔드에서도 결과를 동기로 받으면 평균은 조금 더 빨랐지만 가끔 프레임이 떨어졌습니다. 평균이 약간 늦더라도 **프레임 드랍이 없는 비동기 방식**을 골랐습니다. 사용자가 느끼는 것은 평균이 아니라 끊김이기 때문입니다.

**4. 루프를 프레임에 맞추기**
시간 지연 기반 루프를 프레임 단위로 도는 코루틴으로 바꿔, 한 번 밀린 지연이 쌓이지 않게 했습니다.

## 결과

- 시선 파이프라인 추론 시간 **120–300ms → 42–48ms** (Android)
- 시간이 지나도 밀리지 않고, 프레임 드랍 없음

시선 갱신 주기는 100ms로 고정이라, 추론이 그보다 빨라졌다고 더 자주 돌리지는 않습니다. 대신 갱신 주기 안에 여유 있게 들어오면서 화면이 끊기지 않게 됐습니다.

## 배운 것

- **줄이기 전에 잰다.** "모델이 무겁다"는 가정대로 경량화부터 했다면 시간만 쓰고 끊김은 그대로였을 겁니다
- **GPU가 항상 빠르지는 않다.** 작은 모델, 렌더링과 GPU를 나눠 쓰는 앱에서는 전달 비용과 경쟁이 연산 이득보다 클 수 있습니다
- **평균이 아니라 끊김을 본다.** 중앙값·p95·프레임 드랍을 같이 보고, 판정 기준은 측정 전에 정합니다

## 그다음
