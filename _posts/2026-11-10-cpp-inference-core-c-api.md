같은 비전 파이프라인을 게임 엔진(Unity) 앱과 React Native 앱에 각각 따로 구현해 두면, 같은 모델인데 결과가 미세하게 다르고 최적화도 두 번 해야 합니다. 한쪽에 이미 있던 **C++ 추론 코어**(전처리 → ONNX Runtime 추론 → 후처리)를 C API로 감싸 다른 쪽에서도 쓰게 만든 과정을 정리합니다.

## 1. 왜 같은 모델인데 한쪽이 느렸나

두 앱의 틱 시간을 비교해 보니 한쪽이 두 배 가까이 느렸는데, 모델 단독 시간은 오히려 그쪽 엔진이 빨랐습니다. 차이는 엔진이 아니라 **구조**였습니다.

- 추론 일정 잡기, 결과 확인, 후처리가 **메인(렌더) 스레드**에 묶여 있었고
- 전처리는 GPU에서 하고 결과를 다시 읽어 오며(readback)
- 결과 확인이 렌더 프레임 경계에서만 일어나 틱 하나가 여러 프레임에 걸쳤습니다

추론을 **렌더링과 분리된 전용 스레드**로 옮기는 것이 핵심이었습니다.

## 2. C API 경계 규칙

언어 경계는 두 곳뿐입니다. C# ↔ C(`extern "C"`, P/Invoke)와 Java ↔ C++(JNI). 경계에서 지킨 규칙은 다음과 같습니다.

| 규칙 | 이유 |
|---|---|
| 메모리 배치가 같은 단순 구조체(blittable)만 주고받기 | 마샬링 비용·오류 제거. IL2CPP에서는 P/Invoke가 같은 프로세스의 네이티브 호출과 거의 같음 |
| 구조체마다 `structSize` + ABI 버전 필드, 호출 시 검사 | 플러그인과 앱 버전이 어긋났을 때 조용히 깨지지 않게 |
| **콜백 대신 폴링** | 네이티브 스레드에서 C#으로 거꾸로 부르는 콜백은 IL2CPP 제약이 있고, 작업 스레드에서 엔진 API를 건드릴 위험이 큼 |
| 모든 C++ 예외는 경계 함수 안에서 잡아 반환 코드로 | 예외가 언어 경계를 넘으면 프로세스가 죽음 |
| 수명주기 호출(시작·정지)은 블로킹, 엔진 쪽에서는 작업 스레드에서 호출 | 메인 스레드 멈춤 방지 |

```c
typedef struct {
    uint32_t struct_size;   // sizeof 검사
    uint32_t abi_version;
    uint64_t sequence;      // 새 결과인지 판단
    float    gaze[2], head[3], distance;
    int32_t  valid;
} et_sample;

int et_poll_sample(et_handle h, et_sample* out);   // 새 값이 있을 때만 복사, 반환 코드로 상태 전달
```

## 3. 스레드 구조 — 큐가 아니라 "최신 1칸"

```text
[카메라 스레드] ──프레임 복사──▶ 프레임 슬롯(mutex + condition_variable)
                                        │ 깨움
                                        ▼
                              [코어 작업 스레드] ── ONNX Runtime 내부 스레드
                                        │ 결과 쓰기 + sequence 증가
                                        ▼
                              결과 슬롯(mutex) ◀── [엔진 메인 스레드] 매 프레임 poll
```

- **프레임도 결과도 큐가 아니라 최신 1개만** 둡니다. 늦게 처리할 바엔 최신 프레임으로 추론하는 편이 낫고, 메모리 사용량이 일정합니다
- 카메라 콜백은 버퍼를 곧 재사용하므로, 코어가 그 자리에서 복사해 슬롯에 넣고 조건 변수로 작업 스레드를 깨웁니다
- 엔진은 매 프레임 `poll` 한 번으로 구조체 하나만 복사해 갑니다. 메인 스레드 비용이 거의 0이 됩니다
- 설정 변경은 뮤텍스 + 변경 표시, 자주 바뀌는 게이트 값은 원자 변수로 두고 작업 스레드가 틱 시작 때 읽습니다

## 4. 플랫폼별로 막힌 것들

| 문제 | 원인 | 해결 |
|---|---|---|
| 테스트 종료 시 abort | 정적 객체 소멸 순서에서 ONNX Runtime 환경 객체가 먼저 해제 | 엔진을 프로세스 수명 동안 해제하지 않는 힙 객체로 |
| Android APK에 플러그인 `.so`가 빠짐 | 엔진이 임포트하지 않는 폴더에 둠 | 올바른 플러그인 경로 + ABI 메타 설정 |
| 카메라 소유권 충돌 | 엔진의 카메라와 코어의 카메라가 동시에 장치를 잡으려 함 | 일시정지가 아니라 **닫고 넘기기**, 짧은 지연 후 열고 실패 시 재시도 |
| 모델 파일을 모든 앱이 싣게 됨 | 엔진의 리소스 폴더는 무조건 포함 | 해당 빌드에서만 스트리밍 에셋으로 복사하고 실행 시 해시 확인 |

Android는 NDK로 `arm64-v8a`, 정적 C++ 런타임, 16KB 페이지 정렬로 빌드했고, iOS는 정적 라이브러리 + 정적 ONNX Runtime 프레임워크로 묶었습니다.

## 5. 검증 — 값이 같은지, 프레임이 지켜지는지

- 코어 단위 테스트, C API 테스트(실제 모델 + 합성 영상), 엔진 쪽 테스트, 플랫폼 교차 빌드를 CI로
- 기존 경로와 **출력이 허용 오차 안인지**를 골든 데이터로 비교
- 게임 같은 부하(오프스크린 렌더 + 메인 스레드 작업)를 걸고 틱 시간과 fps, 1% 저점 fps, 20ms 넘는 프레임 비율을 함께 측정

전용 스레드로 옮기자 같은 부하에서 틱 처리 시간이 절반 수준으로 줄었고, 무엇보다 **화면 프레임이 목표 fps에 붙어 1% 저점이 거의 떨어지지 않게** 됐습니다. 메인 스레드가 추론을 기다리지 않게 된 효과입니다.

## 6. 공짜는 아니다

스레드가 달라도 CPU 코어·메모리 대역폭·발열은 나눠 씁니다. 큰 코어가 적은 기기나 장시간 실행에서는 렌더링과 다툴 수 있으니, 스레드 수와 클럭 정책은 기기에서 따로 재야 합니다([모바일 CPU 추론 최적화 점검표](/blog/mobile-cpu-inference-checklist/)).

## 정리

- 같은 모델이 플랫폼마다 느리면 엔진보다 **스레드 구조**를 먼저 본다
- C API 경계: blittable 구조체 + 크기·버전 검사, 콜백 대신 폴링, 예외는 경계 안에서
- 실시간 파이프라인의 슬롯은 큐가 아니라 "최신 1칸"
