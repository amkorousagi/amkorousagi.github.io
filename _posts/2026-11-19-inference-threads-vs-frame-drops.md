게임 엔진 앱 안에서 실시간 비전 모델(작은 CNN 여러 개)을 별도 C++ 추론 스레드로 돌릴 때, 추론 런타임의 스레드 수(ONNX Runtime의 `intra_op_num_threads`, TFLite의 `num_threads`)를 몇으로 둘지 정해야 했습니다. 흔한 답은 "큰 코어 수만큼"입니다. 실제로 재 보니 답이 달랐고, 그 과정에서 **무엇을 재느냐**와 **어떤 순서로 재느냐**가 결론을 바꿀 수 있다는 걸 배웠습니다.

## 1. 무엇을 재나 — 추론 시간이 아니라 화면

처음에는 추론 1회 시간만 봤습니다. 그 기준이면 스레드 2~3이 1보다 빠릅니다. 그런데 사용자가 보는 것은 추론 시간이 아니라 **화면**입니다. 그래서 지표를 바꿨습니다.

| 지표 | 왜 |
|---|---|
| 평균 화면 fps | 목표 fps(30/60)를 지키는가 |
| **하위 1% fps** | 가장 긴 프레임 1%의 fps. 평균이 60이어도 가끔 한 프레임씩 밀리면 여기서 드러난다 |
| 20·33ms 초과 프레임 비율 | 끊김의 빈도 |
| **실제 추론 Hz** | 정한 주기(예: 10Hz)를 실제로 지키는가. 추론이 빨라도 주기를 못 지키면 의미가 없다 |
| 추론 1회 시간 | 참고용. 이것만 보면 결론이 뒤집힌다 |

## 2. 측정 조건을 고정하기

기기마다 결과가 흔들리지 않게 입력과 부하를 고정했습니다.

- **입력**: 카메라 대신 정면 얼굴 이미지 한 장을 계속 넣었습니다. 카메라 수신 비용과 얼굴 움직임을 빼고 추론·화면만 봅니다
- **부하**: 없음 / 인위적 게임 부하(화면 밖 렌더 수천 개 + 메인 스레드 고정 지연). 실제 앱처럼 렌더링이 계속 도는 상황을 흉내 냅니다
- **기준선**: 추적을 끈 상태도 같은 조건으로 재서, 화면 저하가 추론 때문인지 원래 기기 한계인지 구분합니다
- **조합**: 스레드(1·2·3) × 추론 주기(10·20Hz) × 목표 fps(30·60) × 부하(2), 측정 하나는 예열 후 15초
- 기기: 큰 코어가 2개뿐인 구형 iPhone, 구형 Exynos Android 폰(저사양 2종) + M1 태블릿, Snapdragon 8 계열 태블릿(고사양 2종)

## 3. 순서가 결론을 오염시킨다 — 발열

첫 측정에서는 스레드를 늘 **1 → 2 → 3** 순서로 쟀고, "스레드 3이 가장 나쁘다"는 결과가 나왔습니다. 그런데 저사양 폰은 몇 분 측정하는 동안 같은 설정도 화면 fps가 눈에 띄게 떨어졌습니다. 기기가 데워지는 것이죠. 그러면 "3이 나쁘다"가 스레드 때문인지, **가장 나중에 재서**인지 구분이 안 됩니다.

그래서 순서를 뒤집고 되돌린 확인 측정을 따로 했습니다.

```
3 → 2 → 1 → 1 → 2 → 3
```

각 스레드 값이 앞쪽 한 번, 뒤쪽 한 번 나오므로 두 값을 평균하면 시간에 따른 변화(발열)가 스레드마다 똑같이 섞입니다. 실험 설계에서 말하는 **ABBA 균형(counterbalancing)**입니다. 고사양 기기는 처음부터 2회차를 3 → 2 → 1 순서로 재서 본실험 안에서도 균형을 맞췄습니다.

결과:

- 발열을 평균으로 지운 뒤에도 저사양 폰에서 **스레드 1 > 2 > 3** 순서가 남았습니다. 다만 차이는 첫 측정보다 작았습니다. 순서 교란이 차이를 **부풀리고 있었던** 겁니다
- 다른 저사양 폰은 부하가 없을 때 스레드 1만 하위 1% fps가 목표에 붙어 있었고, 2·3은 가끔 한 프레임씩 밀렸습니다
- 고사양 태블릿 하나는 모든 스레드가 같았고(여유가 커서 차이가 안 남), 다른 하나는 게임 부하에서 스레드 1이 몇 fps 높았습니다

## 4. 왜 스레드가 적을수록 화면이 나은가

추론 1회는 스레드가 많을수록 빨랐는데 화면은 반대였습니다. 이유는 **코어 경쟁**으로 봅니다.

- 저사양 기기는 큰 코어가 2개뿐인 경우도 있습니다. 추론 스레드가 큰 코어를 여러 개 잡으면 엔진의 메인 스레드·렌더 스레드와 같은 코어를 다툽니다
- 추론은 100ms마다 짧게 돌고 끝나지만, 화면은 16.7ms(60fps)마다 한 번도 빠짐없이 그려야 합니다. 추론이 잠깐 빨라지는 것보다 **렌더 스레드가 한 번 밀리는 것**이 사용자에게 더 크게 보입니다
- 실제로 게임 부하 상황에서 엔진 메인 스레드의 CPU 점유가 높을 때 스레드 1과 3의 화면 차이가 가장 컸습니다

스레드 1의 대가는 추론 1회 시간이 조금 늘어나는 것뿐이었고, 그래도 추론 간격(20Hz면 50ms) 안에 충분히 들어가 **실제 추론 Hz는 모든 조건에서 설정값을 지켰습니다.**

## 5. 결론 — 등급별로 나누지 말고 단순하게

| 질문 | 결론 |
|---|---|
| 스레드 수 | 기본값 **1**. 어느 기기에서도 화면 지표가 나빠지지 않았고 대부분에서 가장 좋았다. 기기 등급별 분기는 필요 없었다 |
| 예외 | 추론 지연(입력→결과 시간)을 최소화해야 한다면 고사양에서는 2~3이 몇 ms 빠르다. 요구 사항에 그런 기준이 있을 때만 고려 |
| 목표 fps 하한 | 저사양까지 끊김 없이 지키려면 30fps를 하한으로 두고, 60fps는 여유 있는 기기에서만 |
| 통과 기준 예시 | "목표 30fps에서 하위 1% fps ≥ 25, 실제 추론 ≥ 목표 주기의 95%"처럼 화면·주기 지표로 정하면 기기별 판정이 쉬워진다 |

## 배운 것

1. **사용자가 보는 지표로 정한다.** 추론 1회 시간은 부분 최적화다. 같은 앱 안에서 화면 fps, 하위 1%, 실제 추론 주기를 같이 본다
2. **기준선을 같이 잰다.** 추적을 끈 상태가 이미 목표를 못 지키면 그건 추론 문제가 아니다
3. **측정 순서를 섞는다.** 모바일은 몇 분 만에 데워진다. 한 방향으로만 재면 나중 조건이 늘 불리하다. 뒤집어 되돌린 순서(ABBA)로 한 번 더 재면 교란을 걷어낼 수 있다
4. **한계를 적는다.** 기기 종류마다 1대, 고정 이미지, 인위적 부하였다. 실제 카메라·실제 화면에서 같은 지표로 한 번 더 확인하는 것이 다음 단계다
